# 学年会 (grade-meeting) 設計書 —「クラスの状況を持ち寄る同期 Orient の場」

> **位置づけ**: 実装済み (feature/grade-meeting・未マージ) / 設計の**単一正本**。契約ボディは OpenAPI (`registry.ts` + `openapi.yaml`・tag `GradeMeeting`) に、横断仕様は `docs/foundation/` にある。本番反映されたら `docs/features/grade-meeting/` へ graduate し、README 機能表に追加する。
>
> **対象機能**: 学年ごとに、クラスの状況を学年団で持ち寄る。1クラスずつ「事実 → その事実の意味 → 次の一手」を出し合い、次の学年会の冒頭に前回の一手が返る。

**出典**: chimo との設計会話（2026-07-29 構想合意 → 2026-08-07 設計確定） ／ **対象仮説**: Phase2 抱え込み5階層（[retrospective.md](retrospective.md)） ／ **作成日**: 2026-08-07 ／ **ステータス**: 実装済み・本番反映前

---

## 1. 問い

職員室ボード（「会議で話す」タブ）は **読み取り専用の一覧**だった。生徒の様子（クラス別アコーディオン）と情報共有（種別の箱）が並ぶだけで、**人が集まった場で、その場で視点を混ぜる面が無い**。

**問い**: 学年会という既にある場に vitanota を差し込んで、クラスの状況を「持ち寄る」形にできるか。

## 2. なぜ Orient が本丸か

研修（[workshop.md](workshop.md)）で使った OODA デッキ由来の合意（2026-07-29）:

- OODA の4フェーズのうち **Orient（前提の問い直し）だけが構造的に1人でできない**。前提を疑うには外の視点が要る → **プロダクトが介在して初めて価値が出る**。
- 同時に **最も踏み絵-fragile**。観測された瞬間に本音（前提）が嘘になる。Orient では anti-評価が制約ではなく**動作原理そのもの**。

**非同期 Orient は実装済み**（生徒ノート = 1生徒に複数教員の視点／職員室ノートのコメント）。
**同期 Orient が空白**だったので、そこを埋める。非同期で溜めた材料を、同期の場の卓上に出して混ぜる。

## 3. 一文の仮説

> **同じ事実でも、意味づけは人によって違う。それを1つに畳まず並べるから「前提が違う」ことが見える。**

研修の進行表の問い *「同じお題なのに、なぜ違うものができたのか?」* と同じ構造。**1つにまとめた瞬間に Orient は死ぬ。**

## 4. 確定した設計（chimo 2026-08-07）

| 論点 | 決定 |
|---|---|
| クラス状況の中身 | **研修と同じ「観察を集める」形**（担任1人の見立てでも、自動集計でもない） |
| 学年の単位 | `classes` に `grade` 列（教員グループのテーブルは作らない。学年団 = その学年のクラスを見る先生たち、として暗黙に扱う） |
| 段階 | **観察 → 状況判断 → 次の一手** の3段 |
| 数 | **観察は複数・判断も複数・次の一手は1つ** |
| 会の「回」 | 手で「学年会をはじめる」を押したときだけ作る（**自動生成しない**） |
| 週との関係 | 最上部の週ナビに紐づく。**前週へ戻ればその週の学年会がそのまま出る**。過去の週では会をはじめられない |
| 前回の一手 | 今回の冒頭に**表示するだけ**。達成度（できた/一部/できなかった）は採らない |
| 記名 | **無記名**。誰が出したかを画面にも API にも出さない |
| 学年単位のやること | クラスに紐づかない仕事は**既存 tasks に流す**（学年会の中に TODO の仕組みを二重に作らない） |

### 4-1. 段は紙のまま、文言は学年会向けに言い直す

**段の並び（観察 → 状況判断 → 次の一手）は紙の OODA 記録シート（研修の配布物3）と同じ。**
研修で先生が体得した工程をそのまま日常の学年会に持ち込めるのが、この機能の一番の武器なので、ここは動かさない。

一方**文言は 2026-08-07 に chimo が学年会向けに言い直した**。紙の問いかけ形（「〜何が見える?」）から、その欄に書く対象を示す形へ。ワークの最中と違って、学年会ではファシリテーターが問いを読み上げるわけではないため。

| 段 | 見出し | 文言（`src/features/grade-meeting/constants.ts`） |
|---|---|---|
| observe | 観察 | 事実として観察したこと |
| orient | 状況判断 | どんな判断をする？ |
| action | 次の一手 | 次に小さく試してみること |

### 4-2. 学年会がループになる

3段目（次の一手）を持つ理由は、**次の回の冒頭に前回の一手が出るから**。学年会そのものが OODA ループになる。研修のサイクル1→2→3 と同じ構造を、日常の会議で回す。

## 5. 踏み絵ゲートの結果

| 踏み絵 | 通過条件（as-built） |
|---|---|
| 観測された瞬間に壊れる | ◎ 観察・判断は**無記名**（`author_user_id` を API レスポンスに含めない）。未提出者一覧・提出率を作らない。前回の一手に達成度を持たせない。unit test で固定。 |
| 2層を重ねない | ◎ 学年会は教員相互の層。**集計して管理者に見せるビューを作らない**（staffroom 設計書 §3 の境界を維持）。 |
| 生徒を評価しない | ◎ 観察の対象は**クラス**であって生徒個人ではない。生徒個票のスコア化に触れない。 |
| メンタルケア SaaS 化しない | ◎ mood・感情に触れない。事実と意味づけだけ。 |
| ゲーミフィケーション | ◎ 件数・スコア・達成率を出さない。 |
| 語彙 | ◎ 「分析/評価/最適化」を使わず、「観察 / 判断 / 小さく試してみる」。 |

**この機能で一番危ないのは「クラス間の比較」。** 学年会で3クラスを並べると、意図せず優劣が立つ。だから:

- **クラスごとの件数・スコアを出さない**（unit test で固定）
- **並び順はクラス名順で固定**。「活発な順」等のソートを提供しない（repository の `orderBy` で保証）

### 4-4. 生徒ノートを「材料」として観察の直前に置く（chimo 2026-08-07）

クラスカードの**観察欄の直前**に、その週のそのクラスの生徒ノート（印 + 一言）を畳んだ状態で置く（`ClassMaterialNotes`）。非同期で溜めたものを、同期の場の卓上に出す受け渡し。生徒ノートを見ながら「事実として何が見えるか」を書ける。

- **既定は畳む。** 会議の主役は観察を出し合うことで、材料を眺めることではない。
- **クラス単位の合計を出さない。** 撤去した「生徒の様子」セクションは見出しに 😊n / 👀n の集計を出していたが、学年会では3クラスが並ぶので合計を出すとクラス間の比較が立つ。そのため `StudentSupportSection` をそのまま流用せず、**専用の小さなコンポーネントを新設した**（生徒ごとの印と一言だけを並べる）。
- 期間は学年会の週ナビと共通（`useStudentSupport(period)`）。

### 4-5. 生徒ノートを「その日の印象」に作り替える（chimo 2026-08-07）

学年会の材料を見て「コメントしか出ない。Good なのか気になるのか、それに紐づくコメントを出したい」となり、記録の単位そのものを問い直した。

**残したいもの** = 「1人の先生が、1人の生徒について、その日感じた印象」。気軽に残せるよう **サイン（Good / 気になる）だけでもよく**、余裕があればコメントも書く。

これまでは2つに割れていて、**どちらも「今日の印象」を表せていなかった**:

| | 実体 | 問題 |
|---|---|---|
| `student_reactions` | 教員×生徒×種別の**トグル** | 日付が無く、一度 Good を付けるとずっと Good |
| `baton_notes` | 教員×生徒×日付×本文 | **種別が無く**、本文必須なのでサインだけを残せない |

そこで `baton_notes` に `sign` を足して1行で表し、`student_reactions` は**廃止して既存データを移した**（トグル1行 → 付けた日のサインだけの印象1行）。

- **append-only は維持**（chimo 判断）。同じ先生が同じ日に何度でも足せる = 朝と放課後で印象が変わったことをそのまま残せる。
- 「サインも本文も無い」空行は DB の CHECK（`baton_notes_sign_or_content`）と zod の両方で弾く。
- 既存コメント7件は `sign = NULL` のまま（種別なしの行として表示する）。
- **テーブル名は `baton_notes` のまま**据え置き（機能名 baton-relay / 生徒ノート を変えるスコープではない）。意味の正本は migration と schema.ts のコメント。
- 生徒ノートの UI は「印のトグル」→「**今日の印象を残す**」に変わり、Good / 気になる を押すとその日の印象が1行積まれる。
- 学年会の材料では、**コメントがどのサインの行に付いていたかを保ったまま**出す（それが分かってこそ材料になる）。

### 4-3. 学年単位の「やること」は既存タスクに流す（chimo 2026-08-07）

学年会ではクラスに紐づかない仕事も出る（行事の準備・学年通信・保護者対応）。
これを学年会専用の TODO として作ると、**担当・期限・完了の仕組みが `tasks` と二重になる**。

そこで **実体は既存 `tasks`** に作り、`grade_meeting_tasks` は「どの会で決まったか」の紐付けだけを持つ。
研修の `workshop_reflections`（振り返りを既存 `journal_entries` に溶かす）と同じ形。**`tasks` は ALTER しない。**

- 紐付いたタスクは**既存のタスクタブにもそのまま出る** = 学年会の決定が日常の持ち場に流れる。
- カテゴリはテナントの既存カテゴリから選ぶ（既定 = 先頭）。**タスクボードと同じ `/api/task-categories`** を使う（学年会専用のカテゴリは作らない）。
- **担当は学年会では聞かない**（chimo 2026-08-07）。会議中に人を決めさせない。付けたくなったらタスクボードから付ける。付いていれば学年会の一覧にも表示する。
  - 副作用として、担当ゼロのタスクはタスクボードの既定表示（`scope='mine'` = assignee か createdBy）では**書いた本人にしか出ない**。他の先生は絞り込みを「全員」にすると見える。
- 会から外しても**タスク本体は残す**（タスクタブで生きているものを学年会の画面から消させない）。
- 画面上の位置は**クラスカードより前**。学年まるごとの仕事を片づけてから、クラスの話に入る。

タイトル上限は既存タスク作成（`createTaskSchema`）と同じ **15 文字**にそろえる。タスクボードのカード表示がその前提で組まれているため。

**完了チェックが付くことについて**: クラスの「次の一手」には意図的に達成度を持たせていない（前提・見立てを採点しないため）。一方こちらは**業務の TODO** なので、終わったかどうかは普通に業務の話として扱ってよい（情緒データと業務データの線引き）。

## 6. データモデル

| migration | テーブル/列 | 役割 |
|---|---|---|
| `0059_class_grade.sql` | `classes.grade` (INTEGER, NULL 可) | 学年会でクラスをまとめる軸。**NULL 許容 = 既存クラスにバックフィルを強制しない**。学年未設定のクラスは学年会に出さない。 |
| `0060_grade_meeting.sql` | `grade_meetings` | 学年会の1回。`(tenant_id, grade, held_on)` UNIQUE で二度押しでも増えない。 |
| `0060_grade_meeting.sql` | `class_meeting_notes` | 卓上の1行。`kind` = observe / orient / action。`author_user_id` は持つが**返さない**。 |
| `0061_grade_meeting_tasks.sql` | `grade_meeting_tasks` | 学年の「やること」を既存 `tasks` に紐付ける中間テーブル（§4-3）。 |
| `0062_student_impression.sql` | `baton_notes.sign` 追加 / `student_reactions` 廃止 | 生徒ノートを「その日の印象」に作り替えた（§4-5）。 |

- `kind='action'` は **1回×1クラスで1行**（部分 UNIQUE インデックス `class_meeting_notes_action_unique ... WHERE kind='action'`）。observe / orient は何行でも積む。
- 複合 FK `(meeting_id, tenant_id)` / `(class_id, tenant_id)` でクロステナント参照を物理防止。

### 6-1. `grade_meetings` に UPDATE ポリシーを置かない（意図的）

「その日に集まった」という記録は後から書き換わるべきものではないので、UPDATE ポリシーを**置いていない**。
そのため `startMeeting` は `ON CONFLICT DO UPDATE` で書けない（RLS が DO UPDATE を弾く）。
**`onConflictDoNothing` → 入らなかったら既存を SELECT** の2段で表現している。ここを upsert に「直す」と RLS 違反で落ちる。

## 7. 可視性・RLS

`app_role()` CASE パターン（0056〜0058 踏襲）。`ENABLE`+`FORCE`。

| テーブル | SELECT | INSERT | UPDATE / DELETE |
|---|---|---|---|
| `grade_meetings` | tenant-read | tenant 内・`created_by = app_user_id()` | **なし**（§6-1） |
| `class_meeting_notes` | tenant-read | tenant 内・`author_user_id = app_user_id()` | **observe/orient は本人のみ**／**action はテナント内なら誰でも** |

- **observe / orient を本人のみにした理由**: 出した事実は本人が引っ込められる必要がある。他人が消せると場が壊れる。
- **action を誰でもにした理由**: クラスとして1つ決めるものなので、書記が誰でもよい（研修のチーム振り返りと同じ判断）。
- **DELETE で「他人の行」と「存在しない」を区別せず 404 を返す**（`pages/api/grade-meeting/notes/[id].ts`）。区別すると「誰が書いたか」を推測できてしまう＝無記名が API から漏れる。

統合テスト `__tests__/integration/grade-meeting-rls.test.ts`（21 ケース・緑）で、クロステナント遮断・学年フィルタ・二度押しで会が増えないこと・**観察と判断が複数のまま積まれること**・**返り値に author を含めないこと**・一手の1行化と誰でも上書き・観察は本人しか消せないこと・`journal_entries` に行を作らないこと・クラス削除の cascade・**表示中の週の会だけを引くこと**・**やることが tasks に作られ会に紐付くこと**・外してもタスクが残ることを固定。

## 8. API（教員向け `/api/grade-meeting/*`・OpenAPI tag `GradeMeeting`）

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/api/grade-meeting?grade=1&from=..&to=..` | 表示中の週の卓上（クラス + その週の会 + 観察/判断/一手 + 前回の一手） |
| POST | `/api/grade-meeting` | 学年会をはじめる（同学年・同日なら既存を返す） |
| POST | `/api/grade-meeting/notes` | 卓上に1行置く（action は upsert） |
| DELETE | `/api/grade-meeting/notes/{id}` | 卓上から1行引っ込める |
| POST | `/api/grade-meeting/tasks` | 学年の「やること」を1つ起こす（実体は既存 tasks） |
| DELETE | `/api/grade-meeting/tasks` | 会から「やること」を外す（タスク本体は残す） |

契約ボディは `src/openapi/gradeMeetingSchemas.ts` + `registry.ts`。**どのレスポンスにも author を含めない。**

## 9. 動線（chimo 2026-08-07 で再構成）

「会議で話す」タブ（`StaffroomBoard.tsx`）は **週ナビ + 学年会だけ**になった:

1. **週ナビ**（最上部・前週 / 今週）
2. **学年会**（同期 Orient の場）— 学年チップは**実データから**作る（`availableGrades`。中学なら1〜3年しか出ない）

**撤去したもの**（chimo 2026-08-07）:

- **「生徒の様子」**（朝バトンのクラス別集約）。独立したアコーディオンとしては撤去したが、**中身は §4-4 で「材料」としてクラスカードの中に入った**（`useStudentSupport` を流用）。
- **「情報共有」**（kind ごとの箱・ナレッジ箱）。合わせて `BoardCard.tsx` / `boardMeta.ts` / `useBoards` / `useTeacherNames` を削除した（この面でしか使っていなかった）。
  - **投稿は失われない**: keep/concern/thanks/help は「職員室で交流する」タブに出続ける（あちらは kind で除外していない）。入口（`TodayCaptureBox` / `RetroRecommendation` → `postStaffroomBoard`）もそのまま生きている。
  - 失ったのは「種別ごとに箱で並ぶビュー」と「ナレッジ箱（なるほどが付いた投稿の自動集計）」の2つ。
  - `GET /api/staffroom/board` はフロントから未使用になったが、**POST は投稿の入口が使うのでルートは残す**。
- 学年チップで学年を選び、会をはじめるとクラスカードが並ぶ。
- 会の見出しの直下に **クラス目標**をまとめて出す（クラスごとの話に入る前に、その学年が何を目指しているかを揃える）。目標が1つも無ければ枠ごと出さない。**クラスカードの見出しには重ねない**（同じ文言が truncate されて2箇所に出るのを避ける）。
- **前週へ戻ると、その週に開かれた学年会がそのまま読める**（同じ週に複数回あれば直近の回）。
- **過去の週では会をはじめられない**（`todayDate` が表示中の週に入っているときだけボタンを出す）。「その日に集まった」という記録を後から作らないため。
- `/staffroom` 単独ページからも同じものが見える。
