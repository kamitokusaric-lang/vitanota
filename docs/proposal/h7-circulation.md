## 1. 概要

学校の仕事には医療と似た構造的な難しさがある。**ひとりの子どもの全体像は担任・教科担当・養護教諭・
顧問などに分散しているのに、その子に関わる判断は担任ひとりに集まりやすい**（proposal §01）。本機能群は、
朝の出欠という毎日必ずやる動作に「気になる子へのひとこと／印」を溶かし込み、それを次の先生へ手渡す
**バトンリレー**として相互の見守りを支える。そのバトンは、**職員室ダッシュボードで学校知として返り、
反応が生まれ、また書きたくなる**。

2 機能は分断された別物ではなく、**生徒欄を結節点に閉じる一つの循環**として設計する。これは vitanota の
存在理由（PHILOSOPHY §1「学校組織の**循環**を良くする装置」）と裏テーマ（§2「先生と生徒、先生と先生の
間の小さな感情のやり取りが世界を 1mm ズラす」）に正面から噛む。

---

## 2. 一文の仮説（H7）

> **書く → 溜まる → 返る → 反応する → また書く。** この一周が、生徒欄という一点で閉じたとき、
> 投稿は「自分の思ったこと」から「学校として循環する知」に変わる。

- **H7-A（朝のバトンリレー / `baton-relay`）** = 入口。データが溜まる流れ。
- **H7-B（職員室ダッシュボード / `staffroom`）** = 出口。学校知として返り、反応が生まれる流れ。

入口だけでも出口だけでも回らない。**生徒欄で両者が閉じるから循環になる**（§4）。

---

## 3. 踏み絵ゲートの結果

新機能は PHILOSOPHY §4 の踏み絵をすべて通過しなければ作らない。各論点と通過条件:

| 踏み絵 | 論点 | 通過条件（本設計の構え） |
|---|---|---|
| **§1 循環** | 学校組織の循環を良くする装置か | ◎ 循環そのものを UI 構造に落とした（§4）。記録は目的でなく副産物（バトンの動機は報告でなく次の先生への引き継ぎ）。 |
| **§2 裏テーマ** | 小さな感情のやり取りを太らせるか | ◎ ひとこと・気にかけ・リアクション・Thanks/Help ボードはまさに 1mm を起こす装置。痩せさせない。 |
| **§3 2層** | 管理者層と相互関心層を重ねないか | ○ 職員室ダッシュボードは**教員の相互関心層**。既存 school_admin `/dashboard`（組織状態層）とは別物のまま分け、**個票を admin に流さない**（staffroom 側 RLS で物理担保）。 |
| **§4.0 観測** | 教員に「見られている感覚」を生むか | ○ 循環実感スコアは**裏アンケート KPI**でアプリ内スコア化しない。貢献ランキングを作らない。「誰が書いたか」は引き継ぎ用であって採点用ではない。 |
| **§4.1 情緒 vs 業務** | 情緒データを集計・AI 化していないか | ○ バトン本文（子どもの見立て）は情緒寄りの機微を含む → **AI を触れさせない・スコア化しない・admin に個票を見せない**。クラス目標・タスク・業務タグは業務データとして扱う。mood には一切触れない。 |
| **§4.3 AI 出力** | AI が感情代弁・評価・採点をしないか | ○ v1 はふりかえりを**人/ルールベース**に留め、AI 生成は §7 ゲート（§6）。AI を載せる場合も fact+提案のみ・教員無記名。 |
| **§7 AI 週次の凍結** | 2026-04-27 凍結機能を黙って復活させていないか | ○ AI 週次ふりかえりは **v1 では出さない**（§6）。再開は明示的な §7 再決定を要する（backlog に退避）。 |

### 共通の踏み絵ガード（両機能に焼き込む不変条件）
1. **AI を生徒欄本文（`baton_notes.content`）に触れさせない**（要約・分析・推定・スコア化すべて不可）。
2. **「気にかけ」印を数値化しない**（トグルのまま。子どもの採点化を防ぐ）。
3. **貢献ランキング／投稿数の個人可視化を作らない**（投稿者数は裏集計、教員に「あなた何件」を見せない）。
4. **admin に個票を流さない**（staffroom 側 RLS で物理担保）。
5. **リアクションは「同僚のメモへの共感・労い」**であって子どもの評価ではない、と UI コピーで担保。
6. **生徒情報は軽量に保ち、保持期間を区切る**（baton-relay §ライフサイクル。恒久 dossier 化しない）。
7. **循環実感スコアは裏アンケート KPI**。アプリ内に教員へ見せるスコア／ゲージにしない。
8. **UI 語彙は §6 準拠**（渡す・気にかける・残す。分析・評価・スコア・最適化は使わない）。
9. **mood には一切触れない**（最上位の永久禁止。本機能と mood を交差させない）。

> **chimo のガードレールを踏み絵の “計測による運用化” とする。** 実験カードのガードレール
> （**監視感・生徒の特定・負担増**の 3 点）を隔週の自由記述で監視する（§5）。憲法を「思想」で持つだけ
> でなく「観測される指標」にする。

## 4. 循環の構造

```
   【H7-A 朝のバトンリレー / baton-relay】   【H7-B 職員室ダッシュボード / staffroom】
   = 入口・データが溜まる流れ                = 出口・学校知として返り反応が生まれる

  朝の出欠で気になる子に                     各クラスの生徒情報の投稿が見える
  チェック / 一言                                  │
        │                                  コメント・リアクション
        ▼                                  KPT+Thanks / Help / 共有ボード
  次の先生が同じ画面で追記                         │
        │                                         ▼
        ▼                              （ふりかえりを生成: v1=人/ルール、AI は §7 ゲート）
   ┌───────────────────────────────────────────────┐
   │            結節点 = 生徒欄（生徒ページ）          │
   │                                               │
   │   A) 生徒欄に溜まったデータ ──────────────▶ B へ昇る  │
   │       （各生徒欄から職員室ボードに                │
   │         共有コメント・タスクを追加）              │
   │                                               │
   │   B) 職員室ボードのリアクション ◀────────── B から還る  │
   │       （共有コメントへの反応が                    │
   │         生徒欄にも反映される）                    │
   └───────────────────────────────────────────────┘
        ▲                                     │
        │                                     ▼
        └──────────── 循環 ───────────────────┘
     書く意味を感じる → また書く → さらに溜まる → さらに返る
```

**生徒欄が蝶番**である。A→B（共有コメント・タスクが職員室ボードへ昇る）と B→A（リアクションが生徒欄へ
還る）の両方の口を生徒欄が持つことで、循環が閉じる。この**継ぎ目（seam）= 2 機能の連携契約**は、
両機能の design.md に「連携」として記述し相互リンクする（正本データは baton-relay が生徒欄・students を、
staffroom がボード・リアクションを持つ）。

## 5. 計測設計（循環全体を一体で見る）

**A/B を切り分ける固有指標は置かず、「循環が一周したか」を各段階 1 指標で確かめる。** もし循環が途中で
切れたら**どの段階で切れたかが特定できる**のがこの設計の利点。

| 循環の段階 | 指標 | ライン | 計測 |
|---|---|---|---|
| **書く**（入口が機能したか） | 学校知系記録の**参加実人数**（毎週 15 人中何人が 1 件以上） | 導入 4 週で延べ 9 人以上が一度は参加 | システムログ |
| **溜まる→返る**（循環装置が機能したか） | 週次ふりかえり**閲覧率** | **50%以上**（毎週 8 人が開く） | システムログ |
| | 週次ふりかえり**役立ち率**（開いた人の「役立った／来週も見たい」） | **60%以上** | ボタン押下 |
| **反応する**（双方向に繋がったか） | 共有された記録のうち**リアクション付与率** | 一方通行で終わっていない証拠として軽く追う | システムログ |
| **また書く＋全体実感**（回った実感） | **循環実感スコア**（「書いた・見たことが生徒の見守りに役立っている実感」5 段階） | **平均 4.0以上** | 隔週 1 問アンケート（裏 KPI） |

**ベースライン**: 学校知系の参加は実質ゼロ（仕組みがまだない）。需要は全員（アンケート 15/15）。最初の
ラインを「延べ 9 人」に置くのは、壁を持つと答えた 9 人が一度は書く、という意味でアンケートと地続きに読める。

**ガードレール監視**: 隔週の自由記述で **監視感・生徒の特定・負担増** の 3 点を点検。アンケートで既に
懸念を示した 3 名相当の声が増幅していないかを特に見る。

**判定**:
- **成功** = 循環実感スコア 4.0以上を軸に、閲覧率・役立ち率・参加人数がラインを越え、ガードレール違反がない。
- **部分成功** = 一部の段階だけ未達（書く人はいるのに読まれない＝溜まる→返るが弱い／読まれるのに反応が
  ない＝返る→反応が切れている／全部動くのに実感が低い＝一周はするが手応えがない）。**どこで切れたかを
  特定して手を打つ**。
- **撤退** = 参加人数が立ち上がらず、需要があるのに供給が出てこない状態が続く（**入口設計の根本見直し**）。

## 6. 進め方（フェーズ）

**一体（循環として）で立てる。** 計測が循環一周を見る設計のため A/B を分断しない。

ただし **AI ふりかえりは §7 ゲート**のため、当面は分離する:

- **v1**: ふりかえりは**人/ルールベースの「昨日のまとめ・今週のまとめ」**に留め、循環の骨格
  （投稿→閲覧→反応→再投稿）を先に検証する。これにより §7 凍結に黙って触れずに済む。
- **graduate**: AI 生成ふりかえりは、**明示的な §7 再決定**を経て載せる
  （→ [`../foundation/backlog.md`](../foundation/backlog.md) の §7 ゲート項目）。

## 7. 未解決の論点（chimo 判断待ち・横断）

- **AI ふりかえりの §7 再決定** — 人/ルールベースで循環骨格を回した後、AI 生成へ graduate するか。
  制約: 学校知を返す・教員無記名・fact+提案のみ（§4.3）・mood/生徒感情は要約しない・生徒個人を特定しない。
- **ロスター投入方法** — クラス・生徒の登録を手動入力にするか、インポートを用意するか（baton-relay）。
- **養護教諭・SC の健康文脈の扱い** — 健康・配慮事項という機微情報を全教員可視のバトンに乗せてよいか、
  別扱いにするか。

> ※「児童データ保持期間の値」は baton-relay §ライフサイクルで在学期間に紐づけ確定（決め打ち不要）。
> 「生徒情報の可視範囲」は全教員＝確定（baton-relay / staffroom の RLS で物理担保）。
