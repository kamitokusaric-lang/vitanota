# 今日のふりかえり → AIリコメンド機能 設計書

**対象機能**: 「今日のふりかえり」（マイノート＝非公開）に書いた内容をAIが読み、職員室ボード／ノートへの投稿を区分（相談・感謝・ナレッジ・つぶやき）つきでそっとリコメンドする。

**位置づけ**: 校務サイクル②「AIが気づき＋リコメンドを返す」。主に**階層A（認知）**への打ち手であり、出した先で階層C・D・Eにつながる入口。

最終更新: 2026-06-30 ／ ステータス: 設計合意（実装前）

---

## 0. この設計で合意済みのこと

1. **トーンは「気づきは能動的／行動は受け身」の非対称設計**。気づき（自己認識の支援）は積極的に返すが、公開という行動の決定は100%本人に委ねる。
2. **宛先は区分で自動的に決まる**。AIは宛先を選ばない。
3. **関与の重さは宛先の重さと連動する二層モデル**。ボード行き（相談・感謝・ナレッジ）は公開用ドラフトまで提示。ノート行き（つぶやき）は一押しのみで文面は作らない。
4. **デフォルト非公開を絶対に崩さない**。マイノートは残し、公開は書き換え案に対する明示操作。
5. **出したら必ず反応（3リアクション）につながる**。

---

## 1. 設計思想 ―「気づきは能動的／行動は受け身」

リコメンドには2つの動きが含まれる。これを分離することが本設計の核。

| 動き | 方針 | 根拠 |
|---|---|---|
| **① 気づきを返す**（あなたは今これを抱えているかも、と名付ける） | **能動的**でよい。むしろ能動的であるべき | 階層A（認知）の抱え込みは「抱えていること自体に気づいていない」状態。控えめすぎるAIは最も難しいこの層に届かない。名付けは監視ではなく自己認識の支援＝提案書の原則「本人の自己認識のための可視化であり、管理のための監視ではない」と整合 |
| **② 行動を促す**（だから公開しませんか） | **受け身**に徹する。出すか出さないかは100%本人 | 「強制しない」「距離を保ったまま視点を集める」という思想と整合。デフォルト非公開を崩さない |

この非対称性により、「能動的」と「監視ではない／強制しない」の見かけの矛盾が解ける。**"能動的"の矛先を気づきだけに限定する**のが肝。

---

## 2. 宛先と4区分の対応（ルーティング）

宛先は区分で一意に決まる。AIは区分を判定するだけで、宛先選びは発生しない。

| 区分 | 宛先 | 性質 | 効く階層 |
|---|---|---|---|
| 相談 | 職員室ボード | 集約され**会議で扱われる** | C規範・D対人不安・E構造 |
| 感謝 | 職員室ボード | 集約され会議で扱われる | D・循環1 |
| ナレッジ | 職員室ボード | 集約され会議で扱われる | E・循環1/2 |
| つぶやき | 職員室ノート | 常時タイムラインに流れる | 軽い起動・循環1 |

---

## 3. 二層モデル ― 関与の重さ × 区分

AIの関与の強さは「気づき」「文面提示の有無」「押し方の弱さ」の3軸で表され、区分ごとに決まる。

| 区分 | 気づき | 文面 | 押し方 | 付随情報 |
|---|---|---|---|---|
| 相談 | 能動的に名付ける | **ドラフト提示** | 「出すなら会議の議題として扱われます」 | 議題化の補足（個人宛てでない安心） |
| 感謝 | 拾う（誰へ） | **ドラフト提示** | そっと一案 | 宛先（誰への感謝か） |
| ナレッジ | 拾う（再現性） | **ドラフト提示** | そっと一案 | タイトル＋要点 |
| つぶやき | 軽く触れる | **作らない** | 「ノートに出してみては？」 | なし |

**第1層（ボード行き：相談・感謝・ナレッジ）** — consequential で書くのも難しい。だから気づき＋公開用ドラフトまで提示する。
**第2層（ノート行き：つぶやき）** — 低コスト・低ステークス。だから一押しだけ、文面はAIが作らない。

### 具体例

**相談**
> 日誌「連絡帳の返事をどこまで書くか毎回迷う」＋タグ:不安
> → 気づき:「これ、一人で抱えなくていい困りごとかも。同じく迷ってる先生、たぶん多いです」
> → 区分:相談／ドラフト:「連絡帳の返事の分量、みなさんどこで線を引いてますか？毎回迷ってしまって」
> → 補足:「個人宛てではなく、会議の議題として出ます」

**つぶやき**
> 日誌「授業の導入の小ネタがウケた」＋タグ:喜び
> → 「ちょっといい話。職員室ノートにつぶやいてみては？」（文面なし）

## 4. 画面フロー

```
[今日のふりかえり] 書く（テンプレ or 自由）＋気持ち＋気持ちタグ
        │  「書く」タップ
        ▼
[マイノートに保存]  ← ここで完結してもよい（デフォルト非公開は維持）
        │  保存を起点にAI判定を非同期実行
        ▼
[AI判定]  出す価値あり？ ──No──▶ 何も出さない／「今日は無理に出さなくて大丈夫」
        │ Yes
        ▼
[リコメンド提示]
  ・主提案（相談/感謝/ナレッジ）：気づき＋公開用ドラフト＋補足
  ・つぶやき枠（任意・併置可）：一押しのみ
        │
        ├─「このまま出す」──▶ ドラフト確認 ─▶ ボード/ノートへ公開 ─▶ 3リアクションへ接続
        ├─「直して出す」────▶ 本人が編集 ─▶ 公開
        ├─「今日はやめておく」▶ 何もしない（マイノートは残る）
        └─（つぶやき）「出してみる」▶ 投稿入力（素のまま軽く）
```

**鉄則**
- マイノートへの保存と、ボード/ノートへの公開は**別アクション**。公開は移動でなく**コピー**。
- 提示は保存を邪魔しない（保存完了後に控えめに表示）。
- 「今日はやめておく」を常に同じ重さで用意する（見送りが一級市民）。

## 5. 判定ロジック

### 5.1 トリガー（いつ出すか）
- ふりかえり保存を起点に**毎回判定**するが、**提示するのは「出す価値あり」とAIが判断した日だけ**。
- **ゼロ件を許容**。空振りの提示は階層B（コスト）を悪化させるため、無理に出さない。「今日は無理に出さなくて大丈夫」も正しい返し。

### 5.2 区分判定の手がかり
テンプレ欄と気持ちタグを信号に使う。

| 入力 | 主に向かう区分 |
|---|---|
| よかった・続けたいこと（誰かのおかげ） | 感謝 |
| よかった・続けたいこと（再現できる工夫） | ナレッジ |
| よかった・続けたいこと（それ以外） | つぶやき |
| 気になった・困ったこと（助けがいる） | 相談 |
| 気になった・困ったこと（共有まででいい） | つぶやき |
| 次に試したいこと | ナレッジ寄り |
| ネガ寄りタグ（不安・ストレス・疲労・焦り・混乱・無力感）＋気になったこと | **相談**の強い信号 |
| ポジ寄りタグ（喜び・達成感・充実・安心・感謝・気づき） | 感謝／ナレッジ／つぶやき |

### 5.3 件数
- **主提案は1件に絞る**（最も信号の強い区分）。複数候補で迷わせない＝階層B配慮。
- **つぶやきだけは別枠で軽く共存可**（低コストのため、主提案と並べて出してよい）。

### 5.4 安全・プライバシー
- 生徒名・保護者名・個人を特定する情報は**ドラフトから必ず外す**。
- 感情の生々しい表現は和らげる（公開用にトーンを整える）。
- 自傷・強い心理的危機の兆候を読み取った場合は、公開リコメンドを出さず、相談先の案内に切り替える（要・別途ガイドライン）。

## 6. 出力スキーマ（AI → アプリ）

Bedrock（Claude Haiku 4.5）への構造化出力を想定。Zod で受ける契約イメージ。

```jsonc
{
  "surface": true,                  // 出す価値があるか。false なら以下は null
  "primary": {                      // 主提案（最大1件）。なければ null
    "category": "soudan",           // "soudan" | "kansha" | "knowledge"
    "destination": "board",         // category から導出（soudan/kansha/knowledge=board）
    "awareness": "これ、一人で抱えなくていい困りごとかも。同じく迷ってる先生、たぶん多いです",
    "draft": "連絡帳の返事の分量、みなさんどこで線を引いてますか？毎回迷ってしまって",
    "meta": {
      // 相談: { "agendaNote": "個人宛てではなく、会議の議題として出ます" }
      // 感謝: { "recipientHint": "学年の○○先生" }
      // ナレッジ: { "title": "連絡帳の返事の線引き", "points": ["...", "..."] }
    }
  },
  "tweet": {                        // つぶやき枠（任意）。なければ null
    "nudge": "ちょっといい話。職員室ノートにつぶやいてみては？"
    // draft は持たせない（本人が素のまま書く）
  },
  "reason": "ネガ寄りタグ(不安)＋気になった欄に未解決の困りごと。会議で扱える一般性あり"  // ログ・計測用
}
```

**設計上の約束**
- `destination` は `category` から関数で導出する（AIに選ばせない／不整合を防ぐ）。
- `tweet` には `draft` を入れない（つぶやきは文面提示しない、を型で保証）。
- `reason` は本人には出さず、計測と改善のためのログに使う（監視に転用しない＝集計のみ）。

## 7. 非公開 → 公開の橋渡し（最重要の安全設計）

画面に「自分だけが見られる記録としてマイノートに保存されます」と明記されている＝**安心して書ける前提**。これを裏切らないための原則。

1. **原文をそのまま公開しない。** AIが公開用に書き換えた案を提示する。
2. **マイノートはマイノートのまま残す。** 公開は移動でなくコピー。
3. **デフォルト非公開を崩さない。** 公開は常に本人の明示操作。
4. **確認を必ず挟む。** 「このまま出す／直して出す／やめておく」。
5. **見送りを一級市民に。** 「今日はやめておく」を毎回同じ重さで提示。

---

## 8. 出した後の接続（階層D・E）

- 公開した投稿は、既存の3リアクション（**参考になった／お疲れ様です／すてきです**）に必ずつながる。出して無反応＝循環が止まる（階層E）。
- 相談・感謝・ナレッジ（ボード）は集約され、**定例会議で扱われる**確実性が担保される（階層E）。本人にはこの確実性を提示時に見せる（「会議の議題として出ます」）。

---

## 9. 計測指標（階層Aの下位仮説）

| 指標 | 定義 | 何を見る |
|---|---|---|
| 気づき提示率 | 保存セッションのうち `surface=true` の割合 | 空振り/過剰提示のバランス |
| 転換率 | 気づき提示 → 実際に投稿した割合 | 階層Aの中核指標（書く→気づく→出す） |
| 区分別転換率 | 相談/感謝/ナレッジ/つぶやき別の転換率 | どの区分が出しやすい/出しにくいか |
| 見送り率と理由 | 「やめておく」を選んだ割合（任意で理由） | 何が出すことを止めているか |
| 編集率 | ドラフトをそのまま出した / 直して出した割合 | ドラフト品質、書き換えの納得感 |
| 反応到達率 | 出した投稿に初回リアクションが届いた割合 | 階層Eとの接続（出して終わりでないか） |

**倫理**: すべて集計された傾向としてのみ扱う。個人単位の記録を管理者に提示しない（可視化を監視に転じさせない原則）。

## 10. 未決・次に詰める論点

- 区分判定をAI単独に任せるか、テンプレ欄ベースのルールと併用するか（精度と説明可能性のトレードオフ）。
- つぶやき枠を主提案と常に併置するか、主提案がない日だけ出すか。
- 感謝の宛先（誰へ）をどこまで特定するか（名前を出す/出さない）。
- 自傷・危機検知時のフォールバック文言とエスカレーション先（別途ガイドライン）。
- 提示UIの置き場所（保存完了画面 / マイノート詳細 / 通知）。
